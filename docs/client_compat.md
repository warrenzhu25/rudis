# Client library compatibility

Rudis is checked against the most used Redis client libraries by
`scripts/client_compat/run.py`. It starts a standalone rudis (4 shards) and a 3-master
rudis cluster, fetches each library (network needed; cached under `target/client-compat`), and
runs the same scenarios through each library's own API:

| Scenario | What it exercises |
|---|---|
| strings | SET with EX/NX, GET of a missing key (null), TTL, INCRBY, MSET/MGET |
| collections | HSET/HGETALL, RPUSH/LRANGE, SADD/SMEMBERS, ZADD/ZSCORE (a double) |
| pipeline | 1000 pipelined SETs, then 1000 pipelined GETs |
| transaction | MULTI/EXEC, and WATCH aborting EXEC after another client's write |
| pubsub | SUBSCRIBE and PSUBSCRIBE receiving PUBLISHed messages |
| scripting | EVAL, EVALSHA via the library's script helper, after SCRIPT FLUSH |
| blocking | BLPOP woken by another client's RPUSH |
| streams | XADD, XGROUP CREATE, XREADGROUP, XACK, XPENDING |
| scan | SCAN iteration over 500 keys with MATCH/COUNT |
| resp3 | the other protocol from the library's default (RESP3 for RESP2-default libraries, RESP2 for RESP3-default ones) |
| cluster | the library's cluster client: 200 keys across slots, MOVED handling, MSET/MGET with a hash tag |

Libraries speak their default protocol in the other scenarios: **RESP3** for redis-py 8,
go-redis 9 and Lettuce 6, RESP2 for ioredis, node-redis and Jedis. ioredis has no RESP3 support,
hence no `resp3` cell.


## Redis TCL suite over RESP3

The core TCL suites (`scripts/run_redis_test_suite.sh`, 49 suites) also run with every
connection in RESP3, the way the test suite's own `--force-resp3` mode works (its servers start
with `client-default-resp 3`):

```bash
TCL_EXTRA=--force-resp3 RUDIS_EXTRA="--client-default-resp 3" scripts/run_redis_test_suite.sh 16379 all
```

48 of 49 pass. `unit/tracking` fails: its tests read RESP2-shaped invalidation messages from a
redirection client that is RESP3 in this mode (its header notes it "relies heavily on RESP2"),
while rudis, like Redis's `sendTrackingMessage`, sends a RESP3 redirect target `>2 invalidate
[keys]`. Running the suites over RESP3 found that pipelined XREAD/XINFO replies skipped the RESP3
reshaping (fixed) and that `client-default-resp` was ignored (implemented).

## History

The first run (rudis `6054795`) failed redis-py on `strings`, `collections`, `streams` and
`resp3`, and node-redis on `resp3`. go-redis and Lettuce, also RESP3 by default, happen to tolerate
RESP2 reply types. The cause was rudis answering RESP3 clients with RESP2 types: `$-1` nulls
(which make redis-py's RESP3 parser wait forever), arrays instead of maps and sets, bulk strings
instead of doubles. `scripts/client_compat/resp3_diff.py` compares the RESP3 reply shapes of 240
commands with a reference Redis; it found 54 of the first 162 differing from Redis 7.4.2. After the
fixes 2 of 240 differ, neither of which affects these clients: `MEMORY STATS` has no `db.N`
entries, and `CLUSTER INFO` answers outside cluster mode.
